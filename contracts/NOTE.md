# Local Solidity slice: status and blockers

These contracts and tests are local implementation artifacts only. Nothing here is deployed, and passing local tests is not evidence of a working cross-chain integration. A guarded manual testnet script is available in [`DEPLOYMENT.md`](DEPLOYMENT.md); it has only been simulated, never broadcast.

Provisional topology supplied for implementation: Base Sepolia source/destination (84532), Reactive Lasna for the Reactive contract (5318007), and the operator-approved Uniswap v3 USDC/WETH 0.3% source pool `0x46880b404CD35c165EDdefF7421019F8dD25F4Ad`. The full Blockscout pagination run returned 28,727 Swap logs, each verified against a successful RPC receipt and block header; independent proof that the explorer indexed every chain log remains open. A read-only preflight confirmed chain IDs, deployed code at the documented System/proxy and factory/pool addresses, token order, fee and factory lookup. Neither check proves this project's integration, a live callback, or funding. No unverified deployed project addresses or credentials are embedded in contract configuration.

Current official docs list Base Sepolia (84532) and Reactive Lasna (5318007) as supported testnets and prohibit mixing testnet and mainnet roles: [origins/destinations](https://dev.reactive.network/origins-and-destinations#testnet-chains). The current Reactive System address shown in [Reactive contracts](https://dev.reactive.network/reactive-contracts) is `0x8888888888888888888888888888888888888888`; the Base Sepolia callback proxy listed in the same official chain table is `0x476F44b11F5C942c58f4c8E3d0300E5710743585`. `ReactiveRiskGuard` takes its System address as constructor configuration so isolated tests can inject a test-only double; deployment must read back both addresses against the current docs before use. Test doubles exist only in `test/`.

Deployment ordering for the cycle-free destination setup: deploy the Reactive contract first, deploy the vault with that Reactive contract as its expected sender, then call the Reactive contract's owner-only `configureDestinationVault` exactly once. The destination cannot be changed after configuration.

The Reactive and vault `pay(uint256)` entry points are nonpayable provider billing hooks: they transfer the requested amount from their own prefunded native balance to the authorized service provider. Their payable receive/constructor paths are for funding. Official [economy](https://dev.reactive.network/economy) and [callback-contract](https://dev.reactive.network/callback-contracts) docs state the Reactive contract needs REACT (Lasna testnet: lREACT) and the callback destination needs destination-native gas (ETH on Base Sepolia). Required amounts, actual balances, gas limits and delivery behavior are not established by local tests. The vault's `deposit()` itself remains nonpayable and value-free.

Unresolved blockers include actual deployment and verification, callback delivery for these exact contracts, callback gas and funding requirements, independent source completeness, an operationally useful and newly evaluated model (the research-only test precision was 5%), reporter key custody, and genuine end-to-end event/publication/callback reconciliation. Run `neural-brake-preflight` from the installed backend again immediately before any deployment and compare the addresses to current official docs; it is read-only and not deployment approval. The manual scripts have only been simulated and no live write has been made. The vault is explicitly no-value and does not provide production safety.
